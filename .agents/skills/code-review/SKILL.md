# 범용 엔터프라이즈 코드 변경 후 병렬 리뷰 워크플로우

방금 작성/수정한 코드를 **실제 테크 기업의 배포 파이프라인 전 과정(기획/시나리오 ➔ 아키텍처 ➔ 성능 ➔ 사이드이펙트 ➔ 보안/어뷰징/과금방어 ➔ 법무/플랫폼정책 ➔ UX/접근성/데이터호환성/QA/SRE)** 관점에서 병렬 검증하고 결과를 종합해 보고하는 범용 워크플로우다.
어떤 프로젝트(웹, 앱, 백엔드, 클라우드, AI, 커머스, 콘텐츠 등)에서든 프로젝트에 종속되지 않고 즉시 통용된다.

사용자가 전달한 컨텍스트: **$ARGUMENTS**

아래 단계를 **반드시 순서대로** 수행한다. 단계 건너뛰기 금지.

---

## 0단계: 적용 여부 판정

다음 경우에는 **즉시 중단**하고 사용자에게 그 사실만 알린다:

- 단순 파일 읽기/탐색만 한 경우
- 1~2줄 수준의 사소한 오타 수정
- 사용자가 명시적으로 리뷰 생략을 요청한 경우

위에 해당하지 않으면 1단계로 진행한다.

---

## 1단계: 변경 사항 및 프로젝트 컨텍스트 정리

리뷰 에이전트에 전달할 컨텍스트를 먼저 정리한다:

1. **현재 프로젝트의 기술 스택 및 핵심 규칙** (워크스페이스의 `PROJECT_SPEC.md`, `CLAUDE.md`, `README.md`, `package.json`, `build.gradle` 등에서 파악)
2. **변경된 파일 목록과 경로** (절대 경로)
3. **각 파일의 변경 내용 요약** (어떤 함수/클래스/스키마/UI가 무엇을 위해 어떻게 바뀌었는지)
4. **이번 변경의 목적과 요구사항 배경** (대화 맥락 또는 티켓에서 추출)
5. **프로젝트 사실** — `git remote get-url origin`의 마지막 경로에서 `.git`을 떼고 소문자로 바꾼 이름으로 이 스킬 폴더의 `projects/<이름>.md`를 찾는다 (전역 설치는 `~/.gemini/config/skills/code-review/`, 저장소 설치는 `<저장소 루트>/.agents/skills/code-review/`). 있으면 맨 위 생성 표시 줄을 뺀 내용을 `## 프로젝트 사실` 블록으로 만든다. 없으면 1번에서 파악한 내용만 쓴다.
6. **플랫폼 팩** — 바뀐 파일로 고른다. `.kt`·`.kts`·`.java`·`build.gradle`·Android 리소스 `.xml`이면 `packs/android.md`, `.ts`·`.tsx`·`.js`·`.jsx`·`.mjs`·`.html`·`.css`·`.vue`·`package.json`이면 `packs/web.md`. 둘 다 있으면 둘 다 고른다. 팩 파일은 이 스킬 폴더의 `packs/`에 있다. 고른 파일에서 맨 위 생성 표시 줄을 뺀 내용을 `## 플랫폼 팩` 블록으로 만든다. 해당하는 팩이 없으면 생략한다.
7. **프로젝트 기억 (Memory MCP)** — 사이드프로젝트 등 지속적인 학습/주의사항 관리가 필요한 경우, `call_mcp_tool`로 `memory` 서버의 `search_nodes`(query: 현재 워크스페이스 또는 프로젝트명)를 1회 조회한다. 과거에 축적된 아키텍처 결정, 금기 사항, 주의 버그를 `## 프로젝트 기억 (Memory MCP)` 블록으로 만들어 프롬프트에 주입한다. (조회 결과가 없거나 단발성 작업이면 생략)

이 항목들은 **모든 에이전트 프롬프트에 그대로 포함**된다.

## 2단계: 병렬 리뷰 에이전트 실행 (`invoke_subagent` 동시 호출)

변경 성격에 맞춰 아래 핵심 에이전트들을 **단일 메시지에서 동시에** 병렬 호출한다.

### [A] 필수 코어 리뷰 에이전트 (모든 코드 변경 시 기본 병렬 호출 - 8대 관점)

| # | 에이전트 (`subagent`) | 핵심 검증 관점 |
|---|---------------------|---------------|
| 1 | `scenario-checker` | 요구사항(PRD) 충족 여부, UI 탭-데이터 분류/필터 정합성(카테고리 불일치로 인한 항목 누락 방지), 오프라인/네트워크 장애/다국어(HTML data-i18n 속성 및 런타임 UI 다국어 사전 키 매핑 누락 여부)/IME 입력/동시성 경합/디바이스별 엣지 케이스 시뮬레이션 |
| 2 | `architecture-di-agent` (Web·Backend·Mobile 공통, 플랫폼 팩으로 구체화) | 계층 분리, 단방향 의존성, 모듈화/재사용성(OCP), SOLID/DI 설계, 상태 소유권 |
| 3 | `critical-architecture-reviewer` | 반대 관점(Devil's Advocate)에서 구조적 결정 도전, SSOT(단일 진실 공급원) 위반, 스케일 아웃(데이터/트래픽 10배 증가) 시 병목 도전 |
| 4 | `performance-efficiency` | 알고리즘/메모리 효율, 싱글톤/캐싱, 불필요한 리렌더링/DOM 리플로우/CLS, 번들/캐시 용량 예산, DB/네트워크 호출 최소화 |
| 5 | `side-effect-verifier` | 공유 코드(공통 유틸, 서비스, 상태, 베이스 클래스, 캐시/Service Worker) 변경 시 기존 기능/화면/테스트에 미치는 역방향 영향도 및 회귀 검증 |

| 7 | `legal-google-policy-auditor` | **⚖️ 법무 리스크 & 플랫폼(Google/Apple) 정책 준수**: 개인정보보호법(PIPA/GDPR/CCPA) 및 쿠키/동의 정책, Google Publisher/AdSense 유해 콘텐츠 및 무효 트래픽(오클릭 유도) 방지, Google Search 스팸/구조화 데이터(`JSON-LD`) 진실성, YMYL/실정법 면책 고지, API/클라우드 약관, 상표권·저작권·오픈소스 라이선스 검증 |

### [B] 변경 도메인별 자동 추가 호출 에이전트 (해당 변경 포함 시 함께 병렬 호출)

해당 변경인지는 공백 무시 diff(`git diff -w`, 커밋이면 `git show -w <hash>`)로 판정한다. 들여쓰기·줄바꿈만 바뀐 줄은 해당 변경으로 보지 않는다.

| 조건 | 추가 호출 에이전트 | 핵심 검증 관점 |
|------|------------------|---------------|
| UI / 프론트엔드 / 화면 변경 시 | `design-ux-compliance` & `growth-retention-strategist` | 디자인 시스템/토큰 일관성, 카테고리 탭/필터 칩과 데이터 모델 속성 1:1 일치 여부(Orphan 데이터 방지), 다국어 전환 시 레이아웃 텍스트 누락(data-i18n 바인딩 및 런타임 사전 1:1 매핑 누락), 모바일 터치 vs 데스크톱 호버 분기, 뷰포트 클리핑, 접근성(WCAG/ARIA/키보드), 상태별 UI(로딩/빈화면/에러), 사용자 체류시간·전환율(CRO)·마이크로 인터랙션 |
| DB / 스토리지 / 스키마 / 캐시 변경 시 | `data-migration-compatibility-auditor` | DB 스키마 진화(초기 문서 부재/신규 필드 기본값), `localStorage`/캐시 역직렬화 예외 방어, 기존 데이터와의 100% 하위 호환성 |
| 프로젝트 사실 블록의 "규칙 문서" 절 신호에 맞는 변경 | `project-rules-auditor` | 레포 문서에 적힌 규칙·리뷰 체크리스트를 항목별로 대조 (다른 에이전트에는 규칙 문서를 넘기지 않음) |
| 배포 직전 / 외부 SDK 연동 / 테스트 변경 시 | `qa-test-automation-engineer` & `release-sre-readiness-auditor` | 자동화 테스트 커버리지 빈틈(단순 속성 존재 검사로 인한 False Positive 방어, UI 사전 키 전수 대조), 런타임 구문 검증 하네스, 외부 서비스(Firebase/API/CDN) 장애 격리(Graceful Degradation) 및 환경변수 미설정 안전 모드 |

## 3단계: 메인 세션 재검증 및 핵심 추출 (메인 컨텍스트)

에이전트 결과를 모두 받은 후, 메인 세션에서 직접 코드를 다시 확인하며 재검증한다. 각 보고 끝의 `## 발견 목록` 블록을 위치(`file:line`)별로 묶어서 본다.
**에이전트 결과를 그대로 복사해 전달하지 않는다.** 메인 세션이 직접 판단해 걸러낸다:

1. **재검증** — 각 지적을 코드를 직접 열어 사실인지 확인한다.
2. **모순 정리** — 에이전트 간 결론이 어긋나는 부분은 메인 세션이 코드로 직접 판정한다.
3. **오탐 제거** — false positive 로 확인된 지적은 보고에서 **제거**한다.
4. **불필요 정보 제거** — 사용자 결정에 영향 없는 잡음은 **제거**한다.
5. **요구사항 일치 확인** — 사용자의 원래 요구사항과 구현이 실제로 일치하는지 확인한다.

## 4단계: 사용자 보고

3단계에서 재검증을 통과한 **핵심 문제만** 간결하게 요약해 보고한다.

```markdown
## 리뷰 결과 요약

**변경 파일** (N개)
- path/to/file — 한 줄 요약

**핵심 문제** (심각도순, 재검증 통과 항목만)
- [CRITICAL] ... — 위치 + 한 줄 설명 + 수정 제안
- [MAJOR] ...
- [MINOR] ...

**부문별 감사 요약**
- 🏛️ Architecture & Performance: ✅ 이상 없음 (또는 핵심 요약)
- 🛡️ Security & Anti-Abuse (과금/어뷰징 방어): ✅ 이상 없음 (또는 핵심 요약)
- ⚖️ Legal & Platform Policy (법무/구글·스토어 정책): ✅ 이상 없음 (또는 핵심 요약)
- 🎨 UX / A11y / Data Compatibility / SRE: ✅ 이상 없음 (또는 핵심 요약)
```

## 5단계: 반복 (2회차 교차 검증)

2단계 → 3단계 → 4단계를 **총 2회 반복**하여 1회차 수정 사항이 일으킬 수 있는 2차 부작용(Secondary Effect)까지 완벽히 검증한 뒤 최종 통합 보고를 전달한다.

2회차에는 1회차 발견 목록 전체(재검증을 통과한 문제와 오탐으로 걸러진 것을 구분해서)를 프롬프트에 **"이미 확인됨 — 다시 검증하지 말 것"**으로 넣고, 에이전트는 **그 밖에 놓친 문제만** 찾게 한다. 1회차 발견이 0건이면 "1회차 발견 없음"이라고 적고 그대로 돌린다. 1회차 문제를 다시 확인하는 일은 3단계에서 메인 세션이 한다.

---

## 6단계: 사이드프로젝트 지식 저장 (Memory MCP 영구 학습)

리뷰가 최종 완료된 후, **사이드프로젝트에서 반복 발생할 가치가 있는 핵심 교훈**이 발견된 경우에만 지식 그래프에 저장한다:

1. **저장 대상 판정**:
   - 일회성 오타나 단순 실수는 저장하지 않는다.
   - 특정 라이브러리/스택의 치명적 함정, 프로젝트의 확정된 아키텍처 규칙, 사용자가 명시적으로 강조한 피드백만 저장한다.
   - ⚠️ 회사 레포의 사내 보안/기밀 정보는 절대 저장하지 않는다.
2. **저장 방법**:
   - `call_mcp_tool` (`ServerName: "memory"`, `ToolName: "add_observations"` 또는 `create_entities`)을 호출한다.
   - 엔티티 이름: 현재 프로젝트명 (예: `Project-SurvivalWeb`, `Tech-Supabase`)
   - 관측 내용: 간결한 1~2줄 요약 (예: *"Next.js Server Actions에서는 클라이언트 상태를 직접 참조하지 않고 항상 파라미터로 넘겨야 재시도 시 안전함"*)
3. 저장 완료 사실을 사용자 보고 마지막에 짧게 한 줄("🧠 Memory MCP에 프로젝트 교훈 1건을 저장했습니다.")로 알린다.
